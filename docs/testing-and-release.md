# Проверки и Windows-релиз

## Автоматические проверки

Из корня проекта:

```sh
npm ci
npm run lint
npm test
npm run build
```

`build` включает проверки TypeScript main, renderer и тестов, затем production
bundles. Vitest собирает `tests/**/*.test.ts`; общие mock Electron и логирования
заданы в `tests/setup.ts`. По умолчанию нет зависимости от физического шлема,
реального игрового ярлыка или публичного интернета.

| Набор                        | Что проверяет                                                                  |
| ---------------------------- | ------------------------------------------------------------------------------ |
| `tests/shared/`              | Валидация конфигурации, парсеры ADB/батареи/foreground/приложений, scrcpy args |
| `tests/main/modules/`        | Сохранение, гонки runtime, фоновые интервалы, Android launch, локальные ярлыки |
| `tests/main/infrastructure/` | Таймауты, scrcpy lifecycle, USB, время, resolver и метаданные                  |
| `tests/main/bootstrap/`      | Окно/выход/трей через mocks                                                    |
| `tests/renderer/`            | Модели представления карточек, профилей и журнала                              |
| `tests/release/`             | Проверка отказа при неверном SHA архива инструментов                           |

Это не end-to-end тесты реального USB или видео. Число тестов берите из текущего
CI, не используйте его как неизменяемый критерий релиза.

Для отдельной проверки публичных источников обложек на macOS/Linux:

```sh
VRCC_LIVE_ARTWORK=1 npm test -- tests/main/infrastructure/metadata/application-metadata.live.test.ts
```

Тест скачивает реальные данные во временную папку и проверяет повторное чтение
кэша без сети. Обычный `npm test` его пропускает.

Для live-проверки категорий и реальных обложек Steam с последующим offline-чтением:

```sh
VRCC_LIVE_STEAM=1 npm test -- tests/main/infrastructure/steam/steam-library.live.test.ts
```

Тест использует временные fixture-манифесты, а не установленную библиотеку или
аккаунт оператора. Он не запускает Steam/SteamVR и по умолчанию пропускается.

## Подготовка Windows-пакета

Сборку выполняют на Windows x64 или в GitHub Actions:

```sh
npm ci
npm run build:win
```

Команда выполняет последовательно:

1. `tools:prepare:win`: загрузка официального ZIP, SHA-256 по
   [windows-tools.lock.json](../scripts/windows-tools.lock.json), распаковка полного
   upstream-комплекта и manifest хешей файлов. При повторном использовании
   подготовленного комплекта его файлы также проверяются.
2. `build`: TypeScript и Electron/Vue bundles.
3. `electron-builder --win --x64 --publish never`: NSIS и ZIP, включая инструменты,
   сервер, DLL, брендинг, third-party notices и инструкцию.
4. `verify:win`: сравнение хешей всех файлов manifest в `win-unpacked`, наличие
   ресурсов и запуск встроенных ADB/scrcpy с PATH только на System32. Затем
   упакованный Electron сам проверяет resolver и инструменты специальным CLI-режимом.
5. Генерация `SHA256SUMS.txt` и копирование инструкции в `dist/`.

Проверка выполняется на распакованном результате builder. Она не устанавливает
NSIS на пользовательский ПК и не подтверждает физическую USB-связь/видеокадр. Windows-only тест
`tests/release/steamvr-helper.test.ts` компилирует PowerShell/C# helper в режиме
ValidateOnly без загрузки DLL и старта SteamVR; на macOS он пропускается.
Готовые артефакты дополнительно проходят ручную приёмку ниже.

Зафиксированный комплект: scrcpy 5.0.1, ADB 37.0.1. Сгенерированный каталог
`resources/tools/win32-x64` игнорируется Git. Для заранее скачанного официального
архива можно использовать:

```sh
node scripts/prepare-windows-tools.mjs --archive PATH_TO_ZIP
```

При обновлении инструментов нужно обновить lock, проверить SHA и upstream-файлы,
сервер и лицензии в `resources/third-party`, затем повторить Windows CI.
Не заменяйте только `scrcpy.exe`: его сервер и зависимости должны соответствовать.

### Состав выдачи

Для версии `<version>` в `dist/` появляются:

| Файл                                            | Назначение                                                  |
| ----------------------------------------------- | ----------------------------------------------------------- |
| `VR-Control-Center-<version>-win-x64-setup.exe` | Установщик NSIS                                             |
| `VR-Control-Center-<version>-win-x64.zip`       | Полное приложение без установки                             |
| `*-setup.exe.blockmap`                          | Служебная blockmap установщика                              |
| `README-Windows.txt`                            | Краткая инструкция оператора                                |
| `windows-verification.json`                     | Проверка manifest, файлов и версий инструментов             |
| `windows-runtime-verification.json`             | Результат проверки через упакованный Electron               |
| `SHA256SUMS.txt`                                | SHA-256 перечисленных выше файлов, кроме самого списка сумм |

Внутри приложения ожидаются `resources/tools/win32-x64/bundle-manifest.json`,
каталог `scrcpy/` с полным комплектом и `resources/third-party` с лицензиями.
Не добавляйте в пакет локальные конфиги, логи и audit notes. Builder перечисляет
входящие каталоги в [package.json](../package.json); `docs/` в пакет не входит.

## GitHub Actions и публикация

[windows-release.yml](../.github/workflows/windows-release.yml) запускается для PR
в `main`, push тегов `v*` и вручную (`workflow_dispatch`). Используется Node 24,
`windows-latest`, lint/tests/build и upload artifact `windows-x64` со сроком 30 дней.

После успешного Windows job черновик GitHub Release подготавливается:

- Для PR из `release/*` того же репозитория — на commit головы PR.
- Для тега `v<package.version>` — на commit тега. Несовпадение версии отклоняется.
- Обычный PR, fork PR и ручной запуск без tag ref только загружают artifact;
  создание черновика для них не предусмотрено условием workflow.

Draft создаётся/обновляется с заметками из `docs/releases/windows.md`; файлы
прикрепляются с заменой одноимённых. Уже опубликованный релиз workflow оставляет
без изменений. При изменении имён артефактов старые имена автоматически не удаляются:
состав черновика нужно проверить перед публикацией.

Порядок подготовки следующего релиза:

1. Завершить изменения и актуализировать SDD, ограничения, operator README в
   `resources/windows/README-RU.txt` и release notes.
2. Установить нужную версию одновременно в `package.json` и `package-lock.json`
   (например, `npm version <version> --no-git-tag-version`). Не перезаписывать
   уже опубликованную версию новой сборкой.
3. Отправить ветку и открыть PR; проверить CI именно текущего head commit.
4. Проверить target commit, названия/состав файлов, JSON-отчёты и SHA-256 в draft.
5. Выполнить ручную приёмку Windows-пакета и зафиксировать результат в PR.
6. После принятия изменений согласовать merge/tag и публикацию. Ни успешная сборка,
   ни существование черновика сами по себе не означают опубликованный релиз.

Сборки сейчас без цифровой подписи; workflow не публикует релиз автоматически.
Процесс не включает автоматическое обновление установленного приложения.

## Ручная приёмка на Windows и физических Quest

Используйте целевой игровой ПК. Для сценариев нескольких шлемов проверяйте
адресата по реальному изображению/приложению, а не только цвету карточки.

| Сценарий                                              | Что подтвердить                                                                                                                                                       |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Чистая установка и ZIP без ADB в PATH                 | Открывается UI, resolver использует bundled ADB/scrcpy/server, ZIP работает после полной распаковки                                                                   |
| USB: один шлем                                        | Без ручного serial определяется IP, разрешение запрашивается в шлеме, успех только после Wi-Fi и сохранения                                                           |
| USB: несколько шлемов                                 | Есть выбор, TCP/IP включается на выбранном; другой шлем не получает управляющих команд                                                                                |
| USB: нет/unauthorized/потеря кабеля                   | Понятная ошибка, кнопка разблокируется, существующие карточки не меняются                                                                                             |
| USB: шлем не в Wi-Fi / другой ПК-сегмент              | Не сообщается успешное подключение, доступен повтор                                                                                                                   |
| A/B/C подключены, запуск B                            | Показывается B; остановка B не закрывает A/C                                                                                                                          |
| Быстрые connect→disconnect и disconnect во время poll | Поздние результаты не возвращают устаревший connected, reconnect после ручного отключения приостановлен                                                               |
| Stop→start A, stop A→start B                          | Нет второго процесса A до закрытия старого; B управляется независимо                                                                                                  |
| Изменение адреса/удаление/reset во время операции     | Старая трансляция останавливается, позднее состояние не оживляет карточку                                                                                             |
| Wi-Fi off/on и сон/пробуждение                        | Обнаруживается потеря и восстановление, reconnect ограничен; трансляцию повторно запускает оператор                                                                   |
| Библиотека и офлайн                                   | Список/поиск/launch относятся к выбранному шлему, кэш читается без сети, нет ложного успеха при отказе Android                                                        |
| Время                                                 | Установленное время проверяется, запрет прошивки отображается как ошибка                                                                                              |
| Иконки игр на ПК                                      | Реальная Windows .lnk/.exe показывает системную иконку; PNG сохраняется после перезапуска и удаления оригинала; reset возвращает системную, отмена не меняет карточку |
| Steam VR импорт                                       | Несколько Steam-библиотек, только установленный контент с официальной VR-категорией, повтор без дублей и потери PNG/имени, offline-кэш и unresolved                   |
| Подготовка SteamVR                                    | Уже запущен/ещё не запущен, общий запрос при нескольких нажатиях, отсутствие установки и timeout; игра не открывается до успешной проверки                            |
| Франшизные ярлыки                                     | Работают реальные аргументы/рабочая папка, проверена готовность сервера в самой игре                                                                                  |
| Скрытие/трей/выход                                    | Скрытие сохраняет streams и уменьшает телеметрию; при выходе фактически не остаются нежелательные scrcpy                                                              |
| Существующая конфигурация                             | Сохранены имена/профили/ярлыки, явный custom/PATH не сброшен, старый файл нормализуется                                                                               |

Незакрытые гарантии учитывайте по [known-limitations.md](known-limitations.md).
Для замеров PC VR используйте одинаковые игровые условия и отдельно учитывайте
Electron, ADB и scrcpy. Результаты unit-тестов не заменяют эти замеры.
