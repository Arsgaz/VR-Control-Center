# Аудит нескольких шлемов и фоновой нагрузки

Проверен текущий рабочий код 6 ноября 2026 года. Это анализ, исправления runtime
в рамках аудита не вносились. Проверки с задержанными ответами использовали mock
ADB и виртуальное время; физические шлемы и игровой Windows-ПК не измерялись.

## Исправления после аудита: первый этап

Описание ниже сохраняет исходное состояние аудита. После него внесены изменения:

- Управляющие connect/disconnect/start/stop упорядочены отдельно для каждого
  устройства; ручной disconnect приостанавливает автоматические попытки сразу.
- Поколение операции инвалидирует поздние результаты при ручном connect/disconnect,
  смене адреса и удалении, включая повторное создание той же пары id/адрес.
- Автоподключение использует до трёх параллельных worker и изолирует ошибки команд.
- Stop→start одного шлема ждёт фактического закрытия scrcpy. После 2 секунд
  остановки отправляется SIGKILL, ожидание ограничено 5 секундами. Если ОС не
  подтверждает закрытие, возвращается ошибка, а слот остаётся занят во избежание
  дублирующего процесса. Управление другими шлемами доступно.
- Команды ADB после таймаута получают мягкое/принудительное завершение; Promise
  не ждёт бесконечно отсутствующий close (предел ожидания: timeout + 2 секунды).
  Это ограничивает ожидание приложения, но не обещает завершения процесса при
  отказе ОС в его завершении.
- Перед запуском scrcpy проверяется конкретный транспорт ADB; путь custom ADB
  передаётся scrcpy через окружение. Готовность первого видеокадра пока не проверяется.
- На фоновый цикл выполняется один общий `adb devices -l`, с отдельной проверкой
  актуальности результата для каждого шлема. Для 8 подключённых шлемов нормальный
  цикл теперь требует 17 команд вместо 24 (около 102 вместо 144 в минуту при
  интервале 10 секунд, без fallback и ручных действий).
- stdout/stderr scrcpy остаются в технических логах и больше не вызывают сырой
  IPC и повторные обновления runtime/UI.

## Второй этап: фоновый режим и память

- Скрытое или свёрнутое окно переводит runtime в фоновый режим. Если другое окно
  приложения видно, сохраняется обычный режим. Проверка подключения и reconnect
  продолжаются с прежней частотой.
- В видимом окне батарея опрашивается не чаще раза в 30 секунд; текущее приложение
  — с выбранным интервалом. В фоне: батарея не чаще раза в 120 секунд, приложение
  — не чаще раза в 60 секунд. При большем пользовательском интервале фактические
  обновления могут происходить реже. Пропущенный опрос сохраняет прежние значения.
- Возврат окна вызывает обновление без ожидания следующего таймера. Если старый
  запрос ещё выполняется, повторное обновление ставится после него. Ручной refresh
  и обновление после connect/запуска игры обходят ограничения частоты.
- Одновременно выполняются не более двух запросов телеметрии (батарея/foreground,
  включая последовательный fallback внутри foreground). Очередь проверяет поколение
  устройства перед выполнением. Ручные подключения, отключения и запуск scrcpy
  не ждут свободного места в этой очереди.
- Проверка транспортов ADB отделена от ожидания телеметрии: зависший dumpsys не
  блокирует следующий проход обнаружения. Потеря подключения инвалидирует старые
  ответы, а обнаруженное подключение публикуется до получения батареи.
- Оперативный кэш обложек ограничен 256 записями и бюджетом 16 MiB по консервативной
  оценке строк/служебных данных. Вытесняются давно не использованные записи.
  Дисковые файлы сохраняются: вытесненная обложка читается локально без скачивания,
  пока дисковый кэш актуален. Бюджет не ограничивает всю память Electron, активные
  ответы IPC и изображения, декодированные renderer.

Для 8 шлемов при интервале подключения 10 секунд и успешном основном способе
foreground: около 70 команд/мин в видимом окне и 18 команд/мин в фоне вместо
102 после первого этапа (144 до исправлений). В виртуальном времени за две
фоновые минуты проверено 12 списков ADB + 8 запросов батареи + 16 foreground =
36 операций. Это количество команд, а не измерение CPU/GPU или frame time.

Дальнейшие задачи: координация запуска Android-приложений с отключением, проверка
идентичности шлема, контроль готовности видео, ожидание дочерних процессов при
выходе из приложения, сокращение IPC скрытому окну и замеры на игровом ПК.

## Адресация и сценарии

| Сценарий                                               | Текущее поведение                                                                                                                                        |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Подключены A, B, C; запустить картинку B               | `scrcpy --serial IP_B:порт`. Другие шлемы не выбираются автоматически.                                                                                   |
| Остановить картинку B                                  | Завершается дочерний процесс B из `sessions.get(deviceId)`. A и C не останавливаются.                                                                    |
| Отключить B                                            | `adb disconnect IP_B:порт`, остановка scrcpy B, приостановка автоподключения B. Гонки с уже выполняющимися командами остаются.                           |
| Подключить B                                           | `adb connect IP_B:порт`. Получение батареи и приложения использует `adb -s IP_B:порт`.                                                                   |
| Остановить A и сразу запустить B                       | Сессии независимы; завершение A не блокирует B. Автоматического режима «только одна трансляция» нет.                                                     |
| Остановить A и сразу снова запустить A                 | Пока не пришёл `close` старого процесса, запуск отклоняется. Автоматического ожидания завершения нет.                                                    |
| Удалить устройство или сменить адрес во время операции | Старые результаты обычно отсеиваются по id/адресу, scrcpy останавливается. Возврат к тому же id/адресу не защищён поколением операции.                   |
| Пропал Wi-Fi                                           | Опрос обнаруживает потерю транспорта, автоподключение повторяет попытки с задержками 10/20/40/60 секунд. Трансляция автоматически заново не запускается. |
| Изменился IP шлема                                     | Повторные подключения идут на сохранённый адрес. Поиск нового IP и проверка аппаратной идентичности не реализованы.                                      |

Адрес — ключ TCP-транспорта, не аппаратный серийный номер. Если DHCP выдаст старый
адрес другому авторизованному шлему, приложение само не распознает подмену. Для
арены нужны стабильные адреса либо привязка записи к идентичности устройства.

Основной код: `adb.service.ts`, `scrcpy.args.ts`, `scrcpy.service.ts`,
`device-runtime.manager.ts`. Выбор по `--serial IP:порт` соответствует
[документации scrcpy](https://github.com/Genymobile/scrcpy/blob/master/doc/connection.md).

## Проблемы надёжности

### P1. Запоздалый опрос перезаписывает ручное отключение

`refreshRuntime()` запоминает connected из списка ADB, затем ждёт батарею и
foreground. Если в это время закончился `disconnect()`, старый опрос всё равно
записывает connected. Воспроизведение: задержать ответ батареи → отключить шлем
→ завершить ответ батареи. Итог: `connectionState=connected`, но
`suspendedAutoReconnect=true`. UI может предложить трансляцию отключённого шлема.

Причина: `refreshInProgress` защищает только от другого опроса; `updateRuntime()`
проверяет адрес, но не поколение намерения connect/disconnect.

### P1. Подключение и отключение одного шлема не упорядочены

Ручной connect, автоматический connect, disconnect и запуск игры не используют
общую координацию на устройство. UI блокирует свои повторные нажатия, но фоновый
автоподключатель этот UI-lock не видит. Автоподключение не добавляет устройство
в `connecting`, поэтому ручное подключение тоже может пересечься с ним.

Два воспроизведённых случая:

- Задержанный ручной connect завершается после disconnect и возвращает connected.
- Во время незавершённого автоматического connect выполняется disconnect.
  Проверка `suspendedAutoReconnect` отбрасывает поздний результат в модели, но не
  отменяет уже запущенную команду ADB. Фактический порядок изменения транспорта
  зависит от ADB и сети; mock-тест подтверждает пересечение команд, не физическое
  переподключение шлема.

Нужны очередь управляющих действий на устройство, поколение операции и проверка
актуальности после каждого await. Опрос может оставаться параллельным чтением,
но не должен публиковать результаты после смены намерения. Простой общий lock
для всех шлемов создаст новые задержки и здесь не подходит.

### P1. Остановка процесса не имеет гарантированного срока

`ScrcpyService.stop()` отправляет `kill()` и оставляет сессию занятой до `close`.
Если процесс не заканчивается, повторный запуск этого шлема блокируется без срока.
`runCommand()` по таймауту тоже только отправляет kill; Promise завершается лишь
на `close`/`error`. Указанные 10 секунд не являются строгой верхней границей.

Это риск по коду, зависание реального процесса не воспроизводилось. Нужны мягкая
остановка, ограниченное ожидание, принудительное завершение с учётом ОС и уборка
дочерних процессов. Нельзя освобождать слот, пока старый процесс ещё работает.

### P2. Один медленный шлем задерживает автоподключение остальных

В `autoReconnectKnownDevices()` цикл выполняет `await connectAdbDevice()` по
очереди. Воспроизведено: пока A не ответил, B вообще не получает connect.
При недоступных A/B/C задержки складываются; исключение одного connect прерывает
весь текущий проход. Подход: ограниченная параллельность и обработка ошибок
отдельно на устройство, сохраняя порядок операций внутри одного устройства.

### P2. Успех запуска процесса ещё не подтверждает картинку

`spawn` переводит scrcpy в running; IPC уже до этого возвращает `ok=true`.
Проверки готового видеопотока и срока старта нет. Пользователь может получить
сообщение об успешном запуске до ошибки ADB/энкодера/окна. Нужно различать
«запуск запрошен», «процесс запущен» и подтверждённую готовность там, где её
позволяет определить используемая версия scrcpy.

### P2. Настроенный путь ADB не передаётся в scrcpy

Приложение использует `resolver.adb()`, но scrcpy запускается без переменной `ADB`.
Следовательно, настройка custom ADB не гарантирует такой же бинарник внутри
scrcpy: возможен сценарий «подключение работает, трансляция не запускается».
Это вывод из кода; на установленном у пользователя scrcpy не проверялось.
В [официальном исходнике scrcpy](https://github.com/Genymobile/scrcpy/blob/master/app/src/adb/adb.c)
путь берётся из `ADB`, затем из стандартного/portable расположения.

## Фоновая нагрузка

При нормальном ответе foreground один цикл на N подключённых шлемов создаёт:

- N одинаковых `adb devices -l`;
- N `dumpsys battery`;
- N `dumpsys activity activities`;
- дополнительно до N `dumpsys window windows`, если первый способ не дал package.

Для 8 шлемов mock-проверка подтвердила 8 + 8 + 8 вызовов. При стандартном интервале
10 секунд это около 144 коротких процессов в минуту, до 192 с fallback. Это не
оценка CPU. Команды запускаются всплесками: после списка до двух запросов
телеметрии на шлем одновременно, без общего ограничения параллелизма.

`pollInProgress` не даёт перекрывать целые фоновые проходы, а `refreshInProgress`
защищает конкретный шлем от двух опросов. Но зависший проход задерживает опрос
всех шлемов. Периодический таймер просыпается каждую секунду, reconnect — каждые
5 секунд. Сама проверка таймера дешева; основная цель оптимизации — subprocess,
полные dumpsys и лишний IPC.

Сворачивание в трей вызывает `window.hide()`. Интервалы main-процесса не меняются,
отправка runtime/scrcpy в скрытый renderer продолжается. Chromium может ограничить
часть работы скрытого окна, но main-опросы и IPC этим не устраняются.

Каждый chunk stdout/stderr scrcpy вызывает два пути обновления: сырой scrcpy IPC
и runtime IPC через `handleScrcpyEvent()`, даже если статус не изменился. Проверка
100 chunks дала 100 повторных runtime-событий. Это усилитель нагрузки при шумном
выводе, не утверждение о частоте вывода реального scrcpy.

Положительные стороны:

- Config после загрузки хранится в памяти, а не читается с диска на каждый poll.
- Журнал UI ограничен 80 записями, постоянного таймера рендера нет.
- Нет постоянной анимации всего интерфейса; spinner нужен только загрузке библиотеки.
- Обложки загружаются по открытию библиотеки, имеют дисковый/оперативный кэш,
  дедупликацию запросов и четыре worker со стороны окна библиотеки.
- Профиль по умолчанию ограничивает видео 1280, 30 fps, 6M, без аудио.

Оперативный кэш base64-обложек не имеет LRU/общего лимита: после просмотра большой
библиотеки он остаётся в main-процессе до выхода. Это отдельная цель оптимизации
памяти. Видео декодируется отдельным scrcpy; сворачивание Control Center само по
себе не останавливает трансляции и их расходы CPU/GPU/сети.

## Порядок исправлений и приёмка

1. Координация на устройство, отмена/инвалидация старых ответов, строгие сроки
   команд и остановки scrcpy. Не затрагивать другие устройства и не использовать
   глобальный `adb kill-server` для восстановления одного шлема.
2. Независимые попытки reconnect с ограниченной параллельностью; единый путь ADB
   для приложения и scrcpy; корректные состояния старта/остановки.
3. Один список ADB на цикл, отдельная частота батареи и foreground, ограничение
   количества параллельных команд. В фоне более редкая телеметрия, но сохранение
   достаточно быстрого обнаружения потерь и доступности ручного запуска.
4. Дедупликация статусов, буферизация технического вывода, снимок состояния при
   возврате окна вместо постоянного UI IPC, лимит кэша обложек.
5. Замеры production-сборки на игровом ПК: без приложения; приложение с 0/1/8
   шлемами, окно/трей; затем 1 и несколько трансляций; библиотека до/после загрузки.
   Собирать CPU за интервал, private memory/RSS дерева процессов, GPU, диск, сеть,
   число ADB-процессов, p95 времени старта картинки и frame time игры. Для каждого
   режима нужны одинаковые условия игры и отдельный учёт scrcpy/ADB/Electron.

Обязательные сценарии приёмки исправлений: connect→disconnect с поздним connect;
disconnect во время poll; reconnect параллельно ручным действиям; A offline при
рабочем B; stop→start одного шлема; stop A→start B; смена адреса во время операции;
удаление/reset и поздние события; сон/Wi-Fi off/on; unauthorized; зависший ADB и
scrcpy; custom ADB вне PATH; возврат из трея с актуальным снимком состояния.

## Выполненные проверки

Во временном наборе выполнено семь диагностических сценариев: два запоздалых
результата, пересечение auto-connect/disconnect, задержка B из-за A, счётчик команд
на 8 шлемах, повторное создание того же id/адреса, повторные события из вывода
scrcpy. Все семь подтвердили описанное текущее поведение. Временные проверки
удалены после аудита: они фиксировали наличие дефектов, а не желаемые гарантии.
